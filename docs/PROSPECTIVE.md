# Pre-outcome cohort registration and reproducible eligibility

DOCOMO v0.9 introduces a separate study protocol that can be hashed and published **before any test project is created**. Previous `study-audit` hashed a realised list of project IDs, making it impossible to demonstrate that the test population was chosen prospectively. This component addresses the selection-rule problem while deliberately leaving external trust verification as unfinished work.

## Immutable protocol fields

The protocol fixes a unique study ID, UTC registration time, external preregistration URL, domain, accounting currency, selected model, prediction interval coverage, 40-character independent acceptance-oracle commit, oracle owner and a strict measurement policy.

Its three cohorts each contain an explicit, **non-overlapping repository allowlist** and a half-open enrollment window, `[start, end)`. Training and calibration windows must end by registration, and the test window must start at or after registration. Repositories cannot occur in more than one partition. Repository allowlists must be fixed independently of future test outcomes; allowing unregistered additional repositories would invalidate the design.

The measurement policy explicitly requires all seven effort stages measured in minutes, machine currency matching the cohort, all failed attempts, and source ledgers. Unknown protocol fields are rejected instead of silently ignored.

Unlike `study-audit`, the protocol contains **no project IDs, outcome labels, test-set sizes, cost data, or future project manifest references**. It is therefore possible to seal it before any future test work starts:

```sh
docomo protocol-freeze examples/prospective-protocol.json
```

The output is a normalised protocol and its deterministic SHA-256 digest. The example contains fictitious dates and repositories and is **synthetic**.

## Census of every eligible attempted project

Once projects have been enrolled, the `protocol-population` evaluator accepts a document with exactly `protocol`, `expected_protocol_sha256`, `inventory`, and `experiment`. Inventory entries contain only project ID, repository, planning timestamp and either `finalized` or `pending`. Unlike the outcome manifest, an inventory row need not disclose results.

It reconstructs eligibility independently using the sealed repository allowlists and enrollment windows. It checks that each eligible attempt appears in the correctly assigned experiment partition and that no unregistered project is added. It also rejects changed model choice or coverage target, acceptance-oracle substitutions, duplicate IDs, implausible enrollment chronology, changed study domain or currency, and mismatches between the original inventory and project manifests. A pending project is **not** silently treated as a successful, failed, or completed outcome.

A missing eligible project produces `incomplete_eligible_project_census` and an explicit list of excluded identifiers. A complete inventory produces `structurally_complete_pending_external_inventory_and_protocol_audit` and remains **uncertified**, regardless of observed performance.

The enrollment census is not itself proof of true project completeness. A dishonest data provider can conceal an entire project from an inventory; independent reviewers need access to organizational project trackers or an immutable project intake register to detect this.

## Chronology and external evidence

The returned protocol digest is generated by DOCOMO and **does not prove that the protocol existed before outcomes were known**. Any external Git repository, tag, timestamp, or README URL can be edited, recreated or submitted later. External independent verification must retrieve the exact published content by immutable identifier, confirm its digest, validate the server-side publication chronology and compare it with separately authenticated first project start times.

A Git commit's author or committer date alone is self-declared and can be backdated. Do not treat such timestamps, URLs, or a matching in-band digest as an independent research preregistration certificate.

## Recommended study lifecycle

Create and independently publish the protocol digest before any future test work. Maintain a continuously generated, externally auditable registry of **every** candidate project, including failures and pending outcomes. Record non-overlapping activity and machine-billing ledgers throughout development, and retain independent acceptance reports.

At evaluation time, run the enrollment check, then `docomo study-audit` to verify the accounting ledgers, and finally `docomo holdout` against the independently locked future cohort. All three are necessary but **not sufficient** for research certification without external attestation of the underlying evidence and population census.

The current code cannot certify GitHub publication chronology or provenance of source invoices, reviewer identities or acceptance oracles. Issue #17 tracks that external attestation layer. Until then status remains partially calibrated.

## Limitations of fixed repository allowlists

An exact allowlist restricts generality and requires advance knowledge of organizations or repositories. A future protocol version may support reproducible organization-wide rules against an authenticated repository registry, including all newly created repositories, but must freeze those rules before observation, avoid data-dependent exceptions, and audit the inclusion source. The current implementation intentionally supports only explicit stable repository allowlists because implicit regex/prefix selection without an authoritative registry would be difficult to audit.
